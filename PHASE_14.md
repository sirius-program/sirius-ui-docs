# Phase 14 — Alert and Slideover

Alert and Slideover compose the existing Dialog through a package-internal Blade alias that also works with a customized public namespace. No dependency or architecture boundary was added; both use the same lifecycle owner and native modal focus containment.

## Component contracts

Alert accepts required escaped text, an optional escaped title, an optional registered Blade icon, a named footer slot, and the eight standard variants: primary, info (default), success, danger, warning, secondary, ghost, and outline. Content is ordered icon, title, text. The title uses `id-title` and supplies the accessible name; text uses `id-text` as the description. Without a title, text remains the accessible name. Consumer ARIA labels and descriptions take precedence. It uses the existing theme tokens; link remains Button-only. Its entry and exit combine fade and bounce, disabled for reduced motion. Focus and scroll locking remain active until the exit completes. It has no default HTML content slot, header/body props, timers, queues, or automatic application actions. Footer content and business logic belong to the consumer. Its Close button is disabled by default; Escape and backdrop dismissal remain enabled independently. The built-in Close button uses the existing Dialog translation.

Slideover accepts top, right, bottom, or left, defaulting to right. It forwards Dialog header/body/footer props and slots, section classes and IDs, size, closable, dismissal options, and initial focus. The body scrolls independently while header/footer remain visible. Size limits width for left/right and height for top/bottom; full can fill the viewport. Entry and exit slide from the selected edge; reduced-motion preferences disable animations. Focus and scroll locks remain active until the exit finishes.

Both expose the existing Dialog controls and events: data-sir-dialog-open, data-sir-dialog-close, dialog:show/hide requests, and dialog:open/close notifications. Alpine can bind data-open; Livewire supplies open and synchronizes the close event. Use stable IDs and wire:key for Livewire. One Dialog, Alert, or Slideover is active at a time; replacing, removing, or navigating away from one cleans its lifecycle immediately. Nested overlays are unsupported. Native Blade usage requires the package assets, but no Livewire component wrapper.

## Documentation and verification

Separate pages provide copyable Blade Usage per demo, attribute tables, Assets and interaction, State and events, and Translations. Alert demonstrates all eight variants. Slideover has matching Blade and Livewire right-side project forms covering every shipped form control, plus Blade-only left/top/bottom examples. The project forms reuse Dialog sample values and validation rules, with isolated session keys and an invocable Blade submission controller; passwords and uploads are never flashed. Alert is inserted alphabetically in Presentation; Slideover follows Dialog in Layout. Shared field contract is omitted because these are not form controls. The development fixture at `/development/overlays` combines Dialog, Alert, and Slideover examples, covering Alpine and Livewire state, validation, replacement, removal/remounting, and navigation without saving application data. Its layout and fixed-element scroll-lock fixtures are shared.

Package feature tests cover all Alert variants, escaped title/text, accessible names and descriptions with consumer overrides, footer ownership, generated/protected IDs, slot precedence, attribute forwarding, customized namespace composition, all sides, and invalid contracts. Browser coverage exercises fade–bounce timing, title/text rendering and all Alert variants in both themes, confirmation/cancellation, focus, prevented dismissal, all sides, scrollable bodies with stationary headers/footers, mobile themes, full size, real reduced-motion emulation, one active overlay, nested rejection, Livewire updates, cleanup, and sticky/fixed geometry with native and fallback scrollbar preservation. Shared Dialog/Slideover browser cases exercise every form control, file and image uploads, hidden widget sources after updates, readonly/reset actions, toolbar stacking, and datetime positioning during scroll/resize.

Both asset builds passed. Package `composer test` passed (363 tests, 1,148 assertions), docs `composer test` passed (147 tests, 814 assertions), and the complete docs `composer test:browser -- --processes=2` passed (122 tests, 1,396 assertions). The removed `/development/dialog` URL returns 404; its examples now live at `/development/overlays`. Browser selectors target each project form's own trigger, and the native richtext validity test clears content through keyboard selection and Backspace. Lint, type analysis, and Rector checks passed in both projects. The existing architecture tests remain applicable without changes. Cross-version CI remains the compatibility matrix; this local gate verifies the installed framework and browser versions.
